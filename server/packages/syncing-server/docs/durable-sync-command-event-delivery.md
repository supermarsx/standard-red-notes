# Durable sync command event delivery

Durable sync commands commit item, shared-vault, notification, command-journal, and outbox writes in one database transaction. Each outbox row stores a stable `eventId`, and retrying that row republishes the same ID. The shared domain-event message handlers suppress concurrent or recently completed redelivery of that ID within one process. The standalone SQS WebSocket consumer additionally uses a Redis completion marker when the API gateway supplies its shared Redis client.

This is an **at-least-once** contract, not exactly-once delivery. The bounded common consumer cache does not survive a process restart and is not shared by service replicas. A durable cross-service deduplication store is not currently available to every SQS consumer (notably revisions), and external sends cannot share a transaction with the command database. WebSocket SQS delivery is the narrower exception: its Redis marker is shared across API gateway replicas and restarts for the configured TTL.

## Events reachable from a sync command

| Event path                                                                                                                                                            | Consumer behavior                                                                                                                                                                                                               | Remaining duplicate-delivery risk                                                                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ITEM_REVISION_CREATION_REQUESTED` -> `ItemRevisionCreationRequestedEventHandler` -> `DumpItem` -> `ITEM_DUMPED` -> `ItemDumpedEventHandler`/`CreateRevisionFromDump` | Same-process redelivery is suppressed by `DomainEventDeduplicator`.                                                                                                                                                             | A restart or another syncing-server replica can create another dump and revision. Revision creation has no durable source-event uniqueness constraint.                                                                                           |
| `DUPLICATE_ITEM_SYNCED` -> `DuplicateItemSyncedEventHandler` -> `REVISIONS_COPY_REQUESTED` -> `RevisionsCopyRequestedEventHandler`/`CopyRevisions`                    | `CopyRevisions` checks the target for existing revisions and inserts the copy batch transactionally.                                                                                                                            | A race between distinct revisions replicas can pass the pre-check concurrently unless the persistence layer serializes it; the operation remains at-least-once.                                                                                  |
| `ITEM_DELETED` -> revisions `ItemDeletedEventHandler`/`DeleteRevisions`                                                                                               | Repeated deletion is a database no-op after the first removal.                                                                                                                                                                  | Auth's `WebhookItemDeletedEventHandler` can send the public webhook more than once after restart/cross-replica delivery because the webhook dispatcher has no event-id idempotency key.                                                          |
| `ITEM_REMOVED_FROM_SHARED_VAULT` -> `ItemRemovedFromSharedVaultEventHandler`/`RemoveRevisionsFromSharedVault`                                                         | Repeating the association-clearing update is idempotent.                                                                                                                                                                        | Transport delivery is still at-least-once; a concurrent new association would require normal application ordering to prevent a stale removal.                                                                                                    |
| `WEB_SOCKET_MESSAGE_REQUESTED` (including `NOTIFICATION_ADDED_FOR_USER` payloads) -> websocket delivery                                                               | `websocket-gateway/src/sqsConsumer.ts` retains `eventId`; Redis acquire/completion suppresses completed cross-replica and post-restart delivery for the configured TTL. Completed duplicates are acknowledged without dispatch. | If Redis claim/completion is unavailable or indeterminate the message is not acknowledged. A dispatch followed by an unconfirmed Redis completion can still repeat after the processing lease expires. Legacy no-ID events remain at-least-once. |

Tests for the common suppression contract are in `DomainEventDeduplicator.spec.ts` and `SQSEventMessageHandler.spec.ts`. Redis cross-instance reconstruction, failed-claim recovery, completed-duplicate acknowledgement, and fail-closed no-delete behavior are covered by `sqsDedupStore.test.ts` and `sqsConsumer.test.ts`. The natural revision-copy guard is covered by `CopyRevisions.spec.ts`; the durable outbox stable-ID retry is covered by `ExecuteSyncCommand.integration.spec.ts`.
